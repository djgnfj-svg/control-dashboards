문제

구현
  • 오프셋 · 타입(u8 · f32 · f64) · 반올림 선언을 읽는 interpret() 하나
  • 설정은 mtime 캐시로 재시작 없이 반영
  • 짧은 패킷 · 미등록 로봇은 버리고 선언 밖 바이트는 무시

경력 ④ 태스크 할당

두 층 큐

접수 순서로만 돌던 태스크 큐를 배정·로봇별 발행 두 층으로 나누고 우선순위를 넣어, 평소엔 FIFO를 유지하고 긴급 미션만 앞세우도록 구현

문제
  • 접수 순서 큐 하나 — 고장 · 갈 수 없는 로봇에도 배정
  • 급한 일을 앞세울 길이 없음
설계
  • 무엇을 할지(현장별 풀)와 누가 할지(로봇별 큐)를 두 층으로
구현
  • 가까운 가용 로봇에 배정, 다섯 조건은 뺀다
  • 안정 삽입 정렬 — 같은 우선순위는 도착 순, 실행 중인 일은 안 밀린다
  • 1초 틱이 만료 · 배정 · 발행을 뮤텍스 안에서, 네트워크 발행은 밖에서
결과
  • 평소엔 FIFO 그대로 · 우선순위는 API 로 열어 둠
  • 큐 · 상태 · ACK 테스트 134

상태머신 · 명령 ACK

상태
  • 진행 둘 + 닫힘 셋 · 닫힌 기록은 500개까지
ACK
  • 추적 키를 로봇 → 로봇 × 명령으로
  • 늦게 온 이동 ACK 가 취소 추적을 지워 취소한 로봇이 다시 출발하던 문제를 없앴다
재전송
  • 1.5초 유예 뒤 최대 5회 · 이동은 14회
  • STOP · 취소가 나가면 다른 재전송을 끊는다
포기
  • 큐를 지우지 않고 「미배달」 경고로 사람에게
제어권
  • lock_expired() 하나로 판정 — 연결 30초 · 활동 180초, 움직이는 동안은 활동
경력 ④ 명령 ACK · 깊이

취소는 지우지 않고 멈춘다

키
  • 로봇 × 명령 — 늦게 온 이동 ACK 가 취소의 추적을 덮어쓰지 못한다
취소 · 정지
  • 같은 로봇의 다른 재전송을 멈춘다 — 안 멈추면 묵은 MOVE_POS 가 다시 나가 멈춘 로봇이 재출발
지우지 않는 까닭
  • 항목의 intent 가 CANCEL_ACK 를 받았을 때 큐를 정리하는 근거 — 지우면 취소 직후 정지에서 큐가 RUNNING 으로 남는다
결과
  • 회귀 테스트 4 → 25건

화면

관제 — 로봇 목록 · 지도 · 상태 · 제어

  • 로봇을 고르면 위치·배터리·진단이 실시간으로 뜬다
  • 제어권을 잡은 한 사람만 이동·정지·루틴 명령을 낸다
  • 현장 평면도는 보안상 흐렸다
아키텍처

상태는 브로커에서 바로, 명령은 서버를 거쳐

  • 브라우저와 서버가 브로커를 따로 구독하고 같은 스키마로 해석 — 기종이 늘어도 robots.json 만 고친다
  • 명령 · 배정 · 제어권 판정은 서버 한 곳, 1초 틱이 돌린다
아키텍처 · 명령

명령 한 번이 로봇에 닿기까지

명령
  1. REST · 권한
  2. 현장별 대기열
  3. 배정 — 가까운 가용 로봇 · 우선순위
  4. 로봇별 큐
  5. ACK 대기 등록 → 발행
  6. 로봇 ACK
안 닿으면
  1. 1.5초마다 재전송 · 로봇 × 명령별
  2. 포기하면 「미배달」 경고
  3. 큐는 안 지우고 사람에게
  • 접수 순서로만 돌던 큐를 배정·로봇별 발행 두 층으로 나누고 우선순위를 넣어, 평소엔 FIFO · 긴급만 앞으로
  • 로봇당 하나던 ACK 추적을 로봇 × 명령으로 나눠 취소한 로봇이 다시 출발하던 문제 제거 · 회귀 테스트 4 → 25건
  • 클라이언트 타이머 4개가 제각각 내던 제어권 만료를 서버 순수 함수 하나로 모아 먼 길 가던 작업이 끊기지 않게
UI · 성능

맵 에디터 — 조작마다 13초 멈춤

  • 오버레이 4,800개를 조작마다 전부 떼고 다시 붙였다 — 떼는 루프만 8~11초
  • 오버레이를 키로 들고 바뀐 것만 고치는 증분 갱신으로 바꿨다
  • 바뀐 것을 가리는 비교는 순수 함수로 떼어 테스트로 고정

13초대 → 186ms 이내맵 에디터 조작 · 가장 느린 행 클릭 기준

11.4초 → 0.3초관제 지도 레이어 끄기

이력 — 로봇별 하루 가동 타임라인

  • 지난 상태를 되짚을 수 없던 관제에 로봇별 하루 가동·주행·태스크·미배달을 모았다
  • 서버가 로봇 패킷으로 가동률을 직접 센다
현장 연결

영상 · 워치 · 권한

  • HLS 버퍼로 17초 늦던 로봇 카메라를 WebRTC(WHEP)로 전환
  • 로봇마다 따로 보내던 영상을 MediaMTX 로 모아 대수와 무관하게 1회선
  • 관제 PC 로 돌아가야 부를 수 있던 로봇을 Wear OS 워치에서 호출 — 새 길 없이 기존 REST 재사용
  • 관리자·사용자 두 단계 권한에 매니저를 더해 현장 단위로 위임
  • 현장 PC 에서만 하던 제어를 브라우저로 옮겨 제어 절차 10단계 → 2단계
운영

Git 없는 현장 서버에 자동 배포

스테이징
  1. Dropbox 동기화
  2. systemd 감시 · 10초마다 내용 해시
  3. compose 빌드 · 실제 종료 코드
  4. Nginx 거친 헬스 체크 · 최대 60초
  5. OK / FAILED
프로덕션
  1. 트리거 파일 하나
  2. 같은 빌드 · 헬스 체크
  3. 무중단 반영
  • SSH 로 하던 손 배포를 Dropbox 동기화 + systemd 감시 자동 배포로
  • 빌드가 깨져도 「DEPLOY OK」 이던 가짜 신호를 실제 종료 코드·헬스 체크로 바꿔 실패를 FAILED 로
  • 스테이징·프로덕션을 한 호스트에서 나눠, 스테이징에서 잰 뒤 반영
